DECISIONS.md
Архитектурные решения для проекта "Заявки в ремонтную службу"
1. Общая архитектура
Разделение frontend и backend: Backend на Laravel, frontend на Vue 3. Они находятся в отдельных директориях (backend/, frontend/) и работают через API.

Контейнеризация: Полная Docker-среда с несколькими контейнерами:

backend (PHP-FPM + Laravel)

frontend (Node.js для сборки и dev-сервера)

nginx (веб-сервер, прокси для API и раздача статики)

postgres (основная БД)

mysql (БД для тестов, опционально)

redis (для кеширования и очередей, опционально)

Профили Docker Compose:

dev – все сервисы, включая frontend с hot-reload.

test – поднимаются только необходимые для тестов сервисы (postgres, mysql, redis) и backend в режиме тестирования.

prod – минимальный набор: backend, nginx, postgres (или mysql), redis (опционально), frontend статика собирается на этапе сборки образа.

2. База данных
Основная БД – PostgreSQL (используется в dev и prod).

Для тестов обеспечивается возможность переключения между PostgreSQL и MySQL через переменные окружения. В CI тесты прогоняются на обеих СУБД.

Подключения настраиваются в config/database.php; активное соединение задаётся через DB_CONNECTION в .env.

3. Аутентификация и роли
Классическая аутентификация по email/паролю.

Таблица users содержит поля: id, name, email, password, role (enum: dispatcher, master).

Для демо на странице логина добавляются кнопки быстрого входа под предустановленных пользователей (сиды).

Политика видимости заявок:

Диспетчер видит все заявки.

Мастер видит только те заявки, которые назначены на него (assigned_to = его id).

4. Обработка гонок при взятии в работу
Критическая операция перевода заявки из assigned в in_progress выполняется одним атомарным SQL-запросом:

sql
UPDATE requests 
SET status = 'in_progress', updated_at = NOW() 
WHERE id = ? AND status = 'assigned' AND assigned_to = ?;
Если затронуто 0 строк – возвращается 409 Conflict с сообщением, что заявка уже взята или недоступна.

Транзакции используются только для связанных операций (например, запись в аудит-лог), но не для самого обновления статуса.

5. Очереди
Используются для отложенных задач, не критичных к консистентности в реальном времени: отправка уведомлений, запись аудита и т.п.

Драйвер очередей – Redis (через Laravel Horizon или стандартный redis).

6. Аудит действий
Создаётся модель RequestAudit с полями: request_id, user_id, action (created, assigned, taken, completed, canceled), old_status, new_status, old_assigned_to, new_assigned_to, created_at.

Логирование происходит через события модели Request (например, в booted слушаем updated и created).

Аудит можно отключить через переменную окружения FEATURE_AUDIT_LOG=false.

7. Обработка ошибок и UI-уведомления
Собственный компонент Vue Toast.vue для отображения сообщений об ошибках и успехах.

Все ответы API стандартизированы: в случае ошибки возвращается JSON с полями message и (опционально) errors.

На фронте перехватываем ответы и показываем понятные сообщения.

8. Тестирование
Backend:

Unit-тесты для сервисов и хелперов.

Feature-тесты для API-эндпоинтов (проверка статусов, доступов, гонок).

Отдельный тест для проверки параллельных запросов взятия в работу (симуляция через Http::fake() или параллельные вызовы).

Frontend:

Unit-тесты ключевых Vue-компонентов с Vitest (например, форма создания, список заявок).

Базы данных для тестов: оба подключения (pgsql и mysql) проверяются в CI.

9. Деплой (опционально)
Целевой хостинг – Render (бесплатный план).

Docker-образы собираются с multi-stage: сначала сборка фронта в Node, затем копирование статики в финальный образ с nginx.

Переменные окружения для production задаются через интерфейс Render.

10. Управление конфигурацией
Все настройки окружения вынесены в .env (пример в .env.example).

Дополнительные фичи (аудит, сообщения об ошибках) включаются/отключаются через отдельный конфиг config/features.php, значения из .env.
